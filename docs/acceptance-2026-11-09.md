## 三、阻塞交付的问题（P1）

### P1-01：工作台生成的动作类型未注册

**源码确认。** 例如 `src/studio/surface3d.ts:351`、`probability.ts:284`、`polar-parametric.ts:350` 中的生成器直接创建 `create_text`、`create_axes`、`create_circle`。生产目录使用 `text`、`axes`、`circle` 等类型；`src/studio/core/project.ts:39–40` 会拒绝未知积木。不能仅凭局部预览和 action 数量测试判定“一键插入工程”可用。

修复：通过生产 `createAction` / 实际 catalog 生成合法动作，统一字段默认值、ID、对象引用；清查所有工作台，而不只是替换上述三个字符串。

验收：每个工作台的所有预设及至少一个非默认参数组合，均依次通过工程校验、生产编译、保存/重载和真实渲染；测试必须调用生产链路，不能 mock 掉目录与编译器。

### P1-02：生成内容与工作台所见内容不一致

**源码确认。**
- `createSurfaceActions` 仅插入标题、二维 axes 和公式文本，没有参数曲面；把场景 dimension 改为 3d 不会凭空生成 Surface。
- `createProbabilityActions` 丢弃 `_params`，只插入标题、坐标和公式，没有所选分布图像。
- `createPolarParametricActions` 丢弃 `_params`，不同预设都插入固定半径 1.5 的圆，没有对应极坐标/参数曲线。

这与 P1-01 是两个独立问题：修复动作名称后，插入内容仍然不符合预览。

验收：曲面、分布、参数曲线必须使用用户选定的函数、范围和参数；改变参数后工程及实际视频须产生对应变化。若暂未实现，应明确禁用插入并说明限制，不能生成看似成功的占位内容。

### P1-03：分割动画改变结果

位置：`src/studio/timeline-model.ts:splitActionClip`。**模型级复现完成，未进行原生前后对照渲染。**

通用分支把完整动作复制成两份，只修改 duration。例：`scale(factor=2,duration=2)` 分割后执行两次 scale(2)，最终效果成为 4 倍，编译仍无错误。旋转角也可能重复；位移即使按比例分配，非线性 easing 在第二段重新起步，轨迹节奏会改变。

修复：短期只允许语义明确的等待及匀速相对位移；其他动作明确拒绝分割，或先实现可证明等价的分割表示。旋转还涉及枢轴，不应只按角度比例拆分后就宣称等价。

验收：分割前后总时长、最终状态及多个中间时间点一致；覆盖 easing、对象初始状态、重复/嵌套动作及精度误差。不支持的类型应给出清楚反馈。

### P1-04：复制复合片段后仍引用原对象

位置：`src/studio/authoring.ts:134–154`。**模型级复现完成。**

复制 `sequence[circle(name=c), shift(target=c)]` 后，新对象改名为 `c 2`，但复制的 shift 仍指向 `c`；编译通过，副本会操作原对象。

修复：先建立克隆子树中声明对象的旧名→新名映射，再按字段语义改写内部引用；保留对外部对象的引用。可评估复用 `src/studio/blocks/rename.ts`，但须处理 tracker 合法标识符、嵌套 API 参数、表达式和局部变量，不能全局字符串替换。

验收：复制组合中的对象、后续动作、目标变形对象、列表/表达式/API 引用保持内部一致；原对象不受副本动画影响；外部引用不被错误重命名。

### P1-05：API 覆盖声明缺少有效的当前证据

当前名义合并数 **1,731 / 2,293（75.5%）** 不能直接当作当前提交的有效行为覆盖。

审查发现：
- 12 份行为报告的 `package-lock.json` 指纹与验收提交不一致，当前证据校验不能将其全部认定有效；其余被审查源文件指纹匹配，不应笼统说所有源码均过期。
- 按现有注册表 renderer 分类，名义统计为 **Cairo/shared 1,654 / 1,760（94.0%），缺 106 项；OpenGL 77 / 533，缺 456 项**。这些仍是名义计数，尚未扣除弱证据。
- 旧文档把部分条目移作 OpenGL 后写成“Cairo 剩余 53 / OpenGL 剩余 509”，与实际注册表分类口径不同。不能借重新分类将 Cairo 宣称为 100%。
- 剩余项包含 `CairoRenderer.play/render`、`SceneFileWriter.finish/combine_to_movie/encode_and_write_frame` 等实际执行入口，并非全部抽象接口。
- 部分测试存在 `assert True` 或恒成立的非负长度断言；调用存在、返回不报错和实际行为正确必须分层。

具体例子：`src/studio/core/api-families.native.spec-node.mjs:846` 的插件列表、`:986` 的删除非 SVG 文件、`:1016–1017` 的 TeX 错误输出均仅附 `assert True`。对验证器类 API，正例不抛异常可作为有限证据，但还需反例验证；对文件删除/输出等副作用必须检查实际结果。

修复：逐条清理空断言，以状态、数值、文件、像素或视频的可观察变化验证行为；如为抽象/不可直接调用项，给出排除依据并单列，不能记作通过。然后在同一依赖锁文件和源码状态下重新生成全部报告并运行证据校验。

验收：报告必须披露注册总量、支持渲染器、排除项、当前有效行为证据数、UI 可创建数；禁止用注册覆盖、类型可访问或测试条数代替用户可用的端到端 API 覆盖。
